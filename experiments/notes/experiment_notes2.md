# Experiment Notes 02 — Five-campaign expansion, lit-sweeps, and the 4a/4b methodology stress-test

Second session focused on standing up the four remaining `pikp1_*`
campaigns (`avrpia`, `pby2`, `pwt3`, `pwt7`) alongside the existing
`avrpikf` work. Built around an agentic literature-sweep system that
generated per-campaign binding-interface analyses, then assembled
input complexes in ChimeraX, then derived contigs by both Strategy 4b
(literature-derived) and Strategy 4a (geometric interface contacts).
Session was bookended by a hard methodological lesson: when 4b's
literature-derived contigs were found to land on the wrong face of
the receptor for two cross-system campaigns, the resolution was to
acknowledge the literature was insufficient — not to silently fall
back on structural contacts and pretend it was still 4b.

## Structural inputs — assembling complex PDBs

Each campaign needs an assembled binder–target complex PDB to drive
RFDiffusion (the "input mode 2" pre-docked complex). The recipe
varies per campaign because the available templates vary. The pattern
is encoded in a per-campaign `chimerax_assemble_complex.txt` that the
user runs interactively in ChimeraX:

| Campaign | Template strategy | Templates used |
|---|---|---|
| `pikp1_avrpia` | Rung 1 — native complex | AF3 Pikp-HMA + 6Q76 (native Pikp-HMA / AVR-Pia) |
| `pikp1_avrpikf` | Cross-system rung 2 | AF3 Pikp-HMA + 7B1I (OsHIPP19-HMA / AVR-PikF) |
| `pikp1_pby2` | Cross-system rung 2 | AF3 Pikp-HMA + 9TFO (Rmo2-HMA / PBY2) |
| `pikp1_pwt3` | Rung 5+6 + double anchor | AF3 Pikp-HMA + AF3 PWT3 + 6G10 anchor |
| `pikp1_pwt7` | Cross-system rung 2 | AF3 Pikp-HMA + 9TFP (Rwt7-HMA / PWT7) |

The recipe is the same in shape: `matchmaker` AF3 chain A onto the
template's HMA chain, delete alignment-only chains and non-protein,
relabel the effector chain to "B" for pipeline consistency, `combine`,
sanity-check via `contacts`, colour the design region red, save.

Each script ends with the literal `save` path expected by the
campaign's `params.yml`. No effector renumbering — chain B keeps
source-PDB numbering (precursor or 1-based, whichever the deposit
uses), so literature residue numbers map directly into the PDB
without an offset table.

### Iterating on the assembly recipe — three issues

1. **Wrong effector chain in the source PDB.** For `pikp1_pby2`, the
   lit-sweep claimed `9TFO chain B` was PBY2; verification showed
   chains A and B are both Rmo2-HMA (asymmetric-unit dimer) and PBY2
   is in chains C and D. Chain D is more complete in residue range
   (22–84 vs C's 24–84), but only chain C ends up in the binding pose
   relative to chain A after matchmaker — D pairs with chain B in the
   asymmetric unit. The user verified this visually. Same issue exists
   for `pikp1_pwt7` (9TFP chains A,C are PWT7, B,D are Rwt7-HMA);
   pairing is a crystal-packing detail the lit-sweep can't predict.

2. **`setattr` for chain renaming doesn't work.** First attempt at
   relabeling effector chain to "B" used
   `setattr #2/C residues chain_id B`. It returned "Cannot set
   attribute 'chain_id' to 'B'" — `Residue.chain_id` is a read-only
   property in ChimeraX (chain ownership is via the `Chain` object,
   not a residue attribute).

3. **`changechains` argument order.** Second attempt
   `changechains C B #2` failed with "No residues specified have any
   of the 'from' chain IDs." The official ChimeraX syntax is
   `changechains <atom-spec> <new-ID>` (single replacement) or
   `changechains <atom-spec> <current-list> <new-list>` — the atom-spec
   comes **first**. Correct invocation: `changechains #2/C B`. The
   command was webfetched from the ChimeraX docs to verify before
   committing the fix.

## AF3 PWT3 monomer prediction

PWT3 is the only campaign without a deposited structure of the
effector — natural detector is *Rwt3* (a CC-NLR with no integrated
HMA), so PWT3 has never been crystallised in an HMA-binding pose.
Chain B for the assembled complex must come from an AF3 monomer
prediction.

Set up at `experiments/inputs/structures/AF3/pwt3/`:

- `data/A0A223ZP76.fasta` — the input fasta (UniProt entry for the
  B-type virulent allele from Br48).
- `data/pwt3_monomer_af3.json` — AF3 input JSON, mature chain only
  (residues 19–141 of the precursor, 123 residues), modelled on the
  existing `AF3/pikp1_hma/data/pikp1_hma_monomer_af3.json`.
- `alphafold3_pwt3.slurm.sh` — slurm script, modelled on the
  existing pikp1_hma slurm. SBATCH directives, env vars, and the
  reference-DB symlinking block all preserved verbatim.

User ran the slurm on HPC. AF3 returned a model that is **not** a
clean MAX fold: an N-terminal β-sandwich + a long, isolated C-terminal
α-helix sticking out into space. Interpretation deferred. Three
candidate explanations for follow-up: (a) AF3 low confidence in the
C-terminal region; (b) PWT3 genuinely has a non-MAX architecture
(consistent with Le Naour-Vernet 2023's "non-MAX effector"
classification and Inoue 2017's "no detectable similarity to known
domains"); (c) something specific about the sequence (the 12 B-type
substitutions). pLDDT colouring will discriminate (a) from (b).

### B-type vs Ao-type — methodological aside

I initially recommended "the Ao-type is the design target" based on
its description in the lit-sweep as the avirulent allele. User pushed
back and was right: the B-type is what currently infects wheat
carrying *Rwt3*, so a binder against the B-type is the more
translationally meaningful gain-of-recognition design. The Rwt3 →
B-type mapping is a CC-NLR pathway and does not constrain what an
HMA-based binder would do. Both alleles are valid targets (their
folds will be ~identical, so the AF3 monomer is the same
qualitatively). Lit-sweep §3.4's "Ao-type is the design target" was
my interpretive over-reach, not Inoue 2017's claim. Noted but the
file wasn't yet rewritten this session.

## The 4b methodology stress-test

The session's biggest finding. Mid-session, the user assembled the
`pikp1_pby2` complex, ran the ChimeraX colour command for the 4b
contig from the lit-sweep §6.2 (flex pipeline 42–51, claimed to be
β3 of Pikp-HMA), and discovered the red region was on the **wrong
face** of the HMA — facing away from PBY2. The user observed that
the placement of PBY2 looked "almost identical to PikF" (i.e. the
canonical AVR-Pik face), and that the strand actually contacting PBY2
was downstream of α1 (i.e. β2, not β3).

Three things fell out of the diagnosis:

### 1. The lit-sweep's secondary-structure boundaries were guessed

Cross-checking the AF3 Pikp-HMA model and the deposited 6G10 against
the lit-sweep claims:

| Element | Lit-sweep claim | Actual (6G10 SHEET/HELIX records) |
|---|---|---|
| β1 | pipeline ~3–10 | 4–10 |
| α1 | pipeline ~14–30 | **16–27** (over-extended ~5 res) |
| β2 | pipeline ~33–42 | **31–37** (5 residues too long at C-end; what was called "β2" included the β2-β3 loop) |
| β3 | pipeline ~43–49 | 43–48 |
| α2 | pipeline ~60–66 | **52–64** (8 residues too short — actually starts at 52, not 60) |
| β4 | pipeline ~67–73 | 67–73 |

The α2 error means the C-terminal anchor block in the lit-sweep
contigs (`A52-78` for pby2 / pwt7; `A50-68` for avrpikf-style)
actually starts AT or inside α2, not in the β3-α2 loop as claimed.
The α1 over-extension means the proposed "α1 D15/K18-equivalent"
flex region (pipeline 18–22) lands in the middle of the actual α1,
not at one end as a side-chain-contact boundary.

These weren't measured at lit-sweep time. They were inferred from a
mental model of the βαββαβ HMA fold and never cross-checked against
the deposited records. Verified today via `grep HELIX|SHEET` on
6G10.pdb and a backbone-H-bond DSSP-style script run against the AF3
model and 9TFO.

### 2. The lit-sweep's interface descriptions for cross-system campaigns are insufficient

For `pikp1_pby2`: Yu et al. 2025 (the only structural source for the
PBY2 / Rmo2-HMA interface) literally says (page 4):

> "The interface between Rmo2HMA and PBY2 was predominantly mediated
> by polar main-chain interactions between the β3 of Rmo2HMA and β2
> of PBY2 with only limited polar side-chain interactions (D15 and
> K18 from Rmo2HMA and E42 and S48 from PBY2) (fig. S4A)."

That's the entire main-text description. The exact β3 residue range
of Rmo2-HMA isn't named — fig. S4A would resolve it but isn't in the
bioRxiv main PDF. The lit-sweep paraphrased "(~residues 29–38)"
which was speculation.

When the cross-system superposition was actually done (matchmaker AF3
Pikp-HMA onto 9TFO chain A) and the contact residues computed in
9TFO directly, the actual PBY2-contact residues on Rmo2 turned out
to span residues 15–39 — i.e. α1 plus the β2-β3 transition, not β3
proper. Rmo2-HMA also has a short helix at residues 37–41 that
Pikp-HMA doesn't have, which means there's no clean structural
equivalent of "Rmo2 β3" on Pikp-HMA after fold alignment.

For `pikp1_pwt7`: Yu names only **M1 of Rwt7-HMA** by residue. The
description "two faces of Rwt7-HMA" with central side-chains "N39 and
D40 from PWT7" doesn't map to a residue-level Rwt7 flex region; the
lit-sweep §4.1 "INFERRED" tags reflect this. The 4b §6.2 contig that
flexed pipeline 1–30 was the lit-sweep guessing across half the chain.

### 3. The methodological boundary between 4a and 4b matters

Faced with the discrepancy, the obvious move was to compute the
actual contact residues on the structure and use those. The user
called this out:

> "Surely that suggests something is incorrect and the literature
> sweep needs to be revised? ... If the literature can't tell us
> enough information that's an important conclusion, and only then
> should you fall back on the contacts on a solved structure if one
> exists. Because you need to make sure that it is clearly
> differentiated from strategy 4a which selects design regions based
> on contacts with pikp1 in the input complex."

This is correct. Strategy 4a operates on geometric contacts in the
assembled complex. Strategy 4b operates on what the literature
explicitly licenses. Silently switching from "Yu says β3" to "9TFO
contacts span 15–39" and calling it 4b is just 4a with a different
input PDB. The methodological distinction collapses, and the
campaign-level conclusion ("the literature is insufficient for this
target") is hidden.

### The pivot

For `pikp1_pby2` and `pikp1_pwt7`, generated proper 4a contigs via
`contigs_4a.py` against the assembled complexes. Created `v1_4a/`
runs alongside the existing `v1_4b/` directories. ChimeraX scripts
updated so the 4a colour command is active and the 4b version is
commented out, with a header pointer to the lit-sweep file noting
the literature limitation. Left `v1_4b/` runs in place as comparators
(the user can decide whether to launch them).

For `pikp1_avrpia`, also generated a 4a contig as a future option —
but here 4b is well-supported because 6Q76 is a native Pikp-HMA / AVR-Pia
complex with five named contact residues (Varden 2019: S204, S212,
D217, V219, R226). For pia, 4a is a tighter, more selective subset
of 4b's flex window, not a different region. Both contigs target the
same surface. 4b is the active default; 4a is a commented alternative.

## Updates to shared infrastructure

### `sync_to_hpc.sh` — three new excludes

AF3 jobs run on HPC and produce output in
`experiments/inputs/structures/AF3/<prediction>/{AF3_*.out,err,
alphafold3_*_output/}`. Local doesn't have these (the inputs go up
from local; outputs come down only on demand). With `--delete`,
syncing local-to-HPC after submitting an AF3 job would wipe the
running output dir.

Caught when the PWT3 AF3 job was already running on HPC and the next
sync would have wiped it. Three patterns added:

```
--exclude='experiments/inputs/structures/AF3/*/AF3_*.out'
--exclude='experiments/inputs/structures/AF3/*/AF3_*.err'
--exclude='experiments/inputs/structures/AF3/*/alphafold3_*_output/'
```

The curated best-model PDBs that live directly under `AF3/` (e.g.
`AF3/Pikp-1_HMA.pdb`, eventually `AF3/Pwt3.pdb`) are NOT excluded —
they're the input artefacts the pipeline consumes.

A fourth tweak (broad `.nextflow*` exclude for the repo-root
`.nextflow/`) was added then reverted — the user preferred to delete
the stray root `.nextflow/` manually rather than exclude the pattern
broadly.

## Operating constraints — surfaced this session

- **Don't guess secondary-structure boundaries.** I had been quoting
  α1 / α2 / β2 / β3 ranges from the lit-sweep, which itself had
  pulled them from a mental model. The user caught this when I gave
  a flex range that landed in the middle of α1 instead of at its end.
  Going forward: pull HELIX/SHEET records from the deposited PDB, or
  run DSSP on the AF3 model. Show the source.
- **Lit-sweep ≠ structure.** When the literature description is
  insufficient to pin a residue-level flex region, that's a finding,
  not a problem to solve by silently swapping in structural contacts.
  Strategy 4b is "what the literature licenses." If the literature
  says "β3" without naming residues, the contig should reflect that
  uncertainty (e.g. flex a wider region) or the campaign should be
  flagged as 4a-territory.
- **Cross-system alignment is not register-perfect.** Pikp-HMA β3
  doesn't always land where Rmo2-HMA β3 was, because the loop
  architectures differ between HMAs. Fold-based superposition
  preserves overall geometry but not per-strand correspondence near
  divergent loops. Verify by direct contact inspection of the
  assembled complex, not by trusting the source paper's strand label.
- **Effector source-chain identity is a crystal-packing detail.**
  Asymmetric-unit pairing in homodimer-containing complexes (9TFO,
  9TFP) determines which effector copy is in the right pose after
  matchmaker. Visual verification before deletes is mandatory.
- **AF3 effector chain numbering is +N relative to precursor.** When
  AF3 is fed a mature-chain sequence (e.g. PWT3 residues 19–141 fed
  in as positions 1–123), the output PDB is numbered 1–N — so a
  literature reference to "precursor residue 78" maps to AF3 chain
  position 60. This is unavoidable for AF3 monomer outputs. Document
  the offset in the assembly script's header.
- **`changechains` syntax**: atom-spec first, then new chain ID. Not
  `from to model`. ChimeraX docs verified via WebFetch.
- **WebFetch is the right tool for ChimeraX command syntax** — local
  installs don't carry searchable docs.
- **Allele choice is a translational question, not a literature
  question.** B-type vs Ao-type for PWT3: I made a recommendation
  based on the avirulence allele being the "natural" target. The
  user reframed it as which allele is currently infecting wheat. The
  binder-design goal determines the answer, not the lit-sweep's
  framing.
